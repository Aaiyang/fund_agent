# 可选多角色深度研究

基础研究继续默认使用 `strategy="single"`，现有 `standard/deep` 含义保持不变。
移动端在新生成的基金研究、基金对比、持仓诊断和配置分析报告下展示“多角色深度研究”文字链接。
也可以直接提问“多角色研究000001”。股票和板块暂不进入多角色流程。

## 会话入口

报告消息的 `research_id` 由服务端签发。点击链接向现有聊天接口发送一条用户消息及
`research_followup_id`。服务端从当前认证会话的检查点恢复原始问题、已确认基金、账户范围和
拟操作参数，再获取当前证据；不从“进一步研究”这句话猜对象。

未知或其他会话的报告标识返回404；存在未完成图任务时返回409。进一步研究不能与附件或账户
变更混合提交。重复点击已完成的研究会返回已保存报告，不重复取证和调用模型。
升级前没有服务端元数据的历史报告不会展示链接，可以重新明确对象后发起研究。

## Agent 通信

角色按专业基金评价维度设立，且**只在系统真取得到数据的维度上设立**：费率、同类排名与
百分位、换手率、前十大以外的全部持仓、招募说明书的投资范围原文都没有来源，因此不设角色。
让角色分析拿不到的数据，产出只能是套话——这正是这个功能过去一直的效果。

| 角色 | 归属人（署名这一节） | 维度 | 只看这些数据 |
| --- | --- | --- | --- |
| `performance` | 业绩分析师 | 业绩与基准契合 | 分期收益、`get_fund_benchmark`（基准原文、构成权重，成分指数全部可解析时才算超额/beta/alpha/跟踪误差）、共同窗口对比、市场概况 |
| `risk` | 风险分析师 | 风险与回撤 | 净值指标（含最大回撤**及峰谷日期**）、年化波动、夏普与索提诺（`_rf0`：无风险利率按0）、共同窗口风险字段 |
| `holdings` | 持仓与风格分析师 | 持仓与行业风格 | 披露的前十大及上一季权重、增减仓与新进标记、行业配置、关联板块与行情 |
| `manager` | 基金经理研究员 | 基金经理与团队 | 历任区间、合并任期，以及来源页面的「任职回报」列原文 |
| `disclosure` | 披露与来源质量审查员 | 披露与来源质量 | 公告索引（仅标题、日期、重大变更提示，**不含正文**）、市场事件 |
| `portfolio` | 组合配置顾问 | 组合适配 | 持仓与组合账本、事件关联、代码情景。仅在**尝试过**读取持仓时设立，且只有读取成功才运行 |

两张名字表同源（`app/agent/roles.py` 的 `ROLE_OWNERS` / `ROLE_LABELS`），成文节点要逐字复制的
节标题也在那里生成（`### 风险分析师｜风险与回撤`）；移动端进度那一行报的是归属人，不是维度名。
归属人是职务而不是具体的人：只读取数流水线背后没有对应的真实员工，编个名字等于冒充。

切片刻意互不重叠，所以补证只会让「自己那块数据变了」的角色进入修订轮：新增公告到达
`disclosure`，不会到达 `portfolio`。

1. 服务端为**每个角色建一条任务**（不再按「基金 × 角色」展开），声明该角色必须引用哪些
   证据，并持久化证据包与分析起始时间；每个角色另可从不认识的入参表外补取最多四次缺失调用。
   公开研究不查询个人账本，除组合角色外都不接收私人持仓明细。
2. 每个角色除发现外还要给出一个可选的 `stance`：就某个议题（仓位大小、与基准是否契合……）
   表态，并写清什么条件下会翻转。汇合屏障等待全部角色返回；跳过和失败也有明确结果信封，
   不视为赞同。
3. 审核员接收各角色的发现、服务端推导的覆盖、各角色的立场，以及 `cited_evidence`——只包含
   被真正引用到的证据的有界摘录，不再重读整包原文。未知引用、无效反馈和越界基金补证请求
   会被排除并列入缺口。审核规则明确写着：同事的立场不是证据，不要为了凑出分歧而报 issue。
3a. 角色输出后，服务端先做数字审计：结论里的百分数、金额和两位以上小数要能在所引证据中找到；
   `numeric_audit` 只是启发式提示，派生和、四舍五入和单位差异可能未命中，不参与覆盖或状态判定。
3b. 只有同一对象、同一指标出现真实互斥结论时，审核才可填写可选挑战字段（挑战方、发现序号、证据）；
   服务端校验挑战方切片和证据，最多保留两条。挑战只进入被质询角色的一轮修订载荷
   `cross_examination`，不新增辩论节点或额外模型调用；`divergences` 记录是否已回应。
4. 审核可请求最多两项代码构造的独立只读补证：更多公告、经理记录或一周市场事件；相同调用去重。
   覆盖台账还会驱动最多三项补取，只针对角色必需、可重试且尚未成功的调用，并优先补真正失败的项。
5. 缺口由代码分为四类：证据可用但角色未引用、取数失败、未尝试、上游确实不可得。只有前两类进入
   动作：可用未引用直接修订；失败/未尝试先补取，只有拿到可用新证据才修订对应角色；上游为空或
   指标缺失只记缺口，不补取也不修订。审核失败不触发无意义的全员重写。无需修订时保留已审核的
   首轮结果。修订失败也保留首轮发现，但明确标注反馈未解决。
6. 综合节点接收逐项完成矩阵、分歧清单，以及代码配对出的 `tensions`（同一议题、同一对象，
   两个角色的方向严格相反），报告按团队文档成文：每个维度一节、标题用代码给的归属人抬头；
   一节「同事立场与分歧」逐项转写对立（没有对立就如实说明立场一致及原因）；一节
   「行动建议与触发条件」表；最后一节「综合结论与分歧」里每条判断都要点名支持方与反对方的
   归属人并带上真实的 `[ev_…]` 引用。「角色分歧与未解决项」子段逐项转写服务端算出的分歧及其
   是否已被回应。角色共识不是独立事实依据，内部枚举键名不得出现在正文里。

任务ID、发送角色及轮次由服务端赋值。并行通道按 `(run_id, role, round)` 合并，同值重放幂等，
冲突写入或混合任务直接拒绝。证据ID由本轮 turn_id 与实际可见的证据内容哈希得到，
同一份证据在不同角色切片里保持同一标识；引用不存在或本角色不可见证据的结论整体排除。
引用存在不代表语义一定成立，语义支持由审核节点判断，仍需真实模型质量评测。

## 任务完成契约

`research_contract.py` 用代码构造任务，不新增Planner模型调用。**每个角色一条任务**，
不再按「基金 × 角色」展开：任务数量随确认对象数量线性增长时，输出上限会让契约在数学上
无法满足（三只基金对比曾让一个角色拿到4条任务、13个必需来源，而发现上限是4条）。
一条任务声明若干 `EvidenceRequirement{label, tools, scope}`，`scope=per_fund` 要求每个
确认对象都被引用到一次。

角色只返回带证据引用的发现，**不再自报覆盖表**。服务器先剔除引用了不存在或本角色不可见
证据的结论，再从剩下结论实际引用的证据反推覆盖：某块数据或某个对象一条都没引到，就是
没覆盖，靠声明补不回来。全部满足为 `completed`，有存活发现但有缺项为 `partial`，
没有存活发现为 `blocked`。

改为代码推导的原因是实测数据：12次运行里31个角色信封**没有一个**达到 `completed`，
每个 partial 都恰好是4条发现加4条缺口（都撞在schema上限），11次最终结果全是 `partial`，
交叉审核8次失败（其中4次因为没有任何已核验结论可审而瞬时失败）。模型擅长引用、
不擅长记账，所以记账移到代码侧。引用存在仍不代表语义成立，语义支持由审核节点判断，
仍需真实模型评测。

`stance` 是角色仍然自报的唯一一项内容，它被刻意做成"惰性"的：`derive_coverage` 会在立场
自己引用的证据无法核对时丢掉这个观点，但立场永远不进状态表达式、不进覆盖结论、不进缺口
清单。把它接到任何一处，就会重新造出覆盖表当初那扇「必然 partial」的门。对立由代码在事后
从立场配对，所以空清单是合法结果，没有任何一次运行会因为"没吵起来"而判失败。

修订需通过 `addressed_issue_indices` 对应本角色的有效审核反馈。代码检查确认记录是否齐全，
并排除越界确认；这仍不证明语义回应足够。最终报告末尾由代码补充“研究范围核对”，
用中文维度名逐项写明**已覆盖**哪些证据要求，只有缺项才列“缺少 …”；未运行的维度
不参与完成数分母。原始来源标记不完整或过时时，整体状态仍为部分完成。

进一步研究的记忆检索使用原始研究问题。组合角色通过现有画像服务取得已确认约束，并单独接收最多2000字符
的相关历史记忆；截断或未确认的历史表述不能覆盖当前请求或已确认画像。其余维度不接收私人画像与私人账本。

内部分析保存在子图检查点；子图只回传证据、缺口和通信结果，不回传输入会话消息。
用户只接收最终报告文本和独立的 `research_progress` 进度字段，包括取证、分析、审核、补证、
修订和报告阶段。内部模型流不会混入回答，图表继续经过服务端引用校验。

## 执行与限制

沿用父图PostgreSQL检查点和会话执行锁。报告生成失败或断线后，可通过既有“继续已确认的任务”
入口恢复未完成节点。若多角色子图里已有失败角色，续跑会以同一确认任务新开一轮多角色研究，
避免只从 `write_report` 补写降级稿；角色成功、仅最终成文失败时仍原地恢复，不重跑角色与取证。
单角色或审核失败在未续跑时会生成披露缺口的部分报告。

角色调用使用既有用户模型配置、结构化输出、tenacity重试/降级及继承的Langfuse追踪。
无工具的独立调用不会修改共享工具绑定或用户当前模型索引。

- `FUND_MULTI_ROLE_RESEARCH_CALL_TIMEOUT=60`：每次角色/审核/修订调用的超时秒数。
- `FUND_MULTI_ROLE_RESEARCH_TOTAL_TIMEOUT=180`：角色通信阶段的总预算，包括补证；恢复时不重置。
  初始取证和最终报告仍使用已有独立期限。达到预算后保留已有结果并明确返回部分完成。
- `FUND_MULTI_ROLE_RESEARCH_MAX_TOKENS=8192`：结构化输出上限，限制在1024–65536。
  实测21次角色/审核调用最大输出4262 token、`finish_reason=length` 零次，原来32768是空转；
  现在留约2倍余量，因为GLM把隐藏推理也计进同一个额度。
- `FUND_MULTI_ROLE_RESEARCH_REASONING_EFFORT=low`：只发给GLM-5.3系列。high档下每次角色
  调用45-85秒，且77次调用里27次 `output_chars=0`，额度几乎全花在界面看不见的隐藏推理上。

最多十一次结构化调用：六个角色分析、一次审核、六次修订（公开研究没有已核验持仓时是五个角色）。
工具补取最多五项：审核请求两项 + 覆盖台账三项，不增加模型调用。延迟目标是接近单档加一个审核轮次，
**尚未用真实供应商复测**，所以这是预算不是结论。
内部进度和公开答案继续分离；移动端不会被迟到的首轮事件退回旧阶段或重新显示已完成角色为进行中。
日志新增角色与审核耗时、输入字符数、任务覆盖数、补证数与取得台账的 ok/empty/failed/not_attempted
计数，便于区分模型等待、证据读取和工作流开销。
当前版本在会话请求内执行，支持进度、取消与检查点继续，尚未增加独立Taskiq研究后台任务。
模型供应商需要支持现有LLM服务的结构化输出路径。自动化测试使用模型和工具替身；真实模型的
研究质量、供应商兼容性、耗时和成本还需通过线上配置及评测验证。

## 离线多角色 fixture 评测

`evals/fixtures/multi_role/cases.json` 保存固定证据包和期望；`evals/multi_role_eval.py` 直接驱动真实
多角色子图（模型、工具、审核都是确定性替身），不联网、不写数据库。运行：

```bash
python -m scripts.eval_multi_role --output .runtime/multi-role-eval.json
```

报告包含每个 case 的覆盖状态、未知引用数、修订角色、重复结论数、调用次数和估算 token；汇总给出
未知引用率、平均调用数和最大图耗时。`tests/test_multi_role_eval.py` 把它作为 pytest 回归门。
按服务端推导覆盖的契约重测后，五轮中位数为：固定双轮参考调度320.33ms（五个维度、永远两轮、11次结构化调用），
优化图229.16ms（6次：五个维度并行首轮加一次无问题审核，不修订）。它不含初始取证、最终报告或真实模型，
不能用来承诺线上整体提速比例。测量输出在 `backend/.runtime/multi-role-benchmark.json`。
`python -m scripts.compare_research_modes --yes-live --fund-code <代码>` 是它的真实模型对应物：同一个问题
在打着的API上跑两个档位，回报客户端真正看得见的指标——首字延迟、总耗时、小节与引用计数、代码生成的尾注，
以及 `research_progress`/`research_activity` 帧数。结果写 `backend/.runtime/research-mode-comparison.json`，
这条命令绝不能进CI。
首次真实基线（2026-10-18，glm-5.3-flash，000001，同一问题同一会话）：单档首字38.41秒、总75.58秒、
25处引用零处无法核对；多角色首字97.5秒、总129.98秒、24处引用零处无法核对，`research_progress` 27帧、
`research_activity` 0帧。两档现在都带代码生成的来源核对，只有多角色带维度小节与范围尾注。
活动帧为0是结构性的：`ProgressChatOpenAI` 有意只保留 `reasoning_content` 的**长度**不保留正文，
而 function_calling 的每个分片 `token` 都是空串，所以 `services/llm/timeouts.py` 的观察器永远收不到片段。
要修得先定产品口径（改发「已思考N字」这种无害行，或干脆不下发这个字段），不能靠把隐藏推理透给客户端来「修好」。

上线后使用相同模型和研究对象观察角色阶段耗时、完整/部分完成率、人工检查的事实支持率；
只有速度和质量同时达标才调整预算或进一步压缩上下文。当前未做真实供应商报告质量评估。
