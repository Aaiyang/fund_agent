## 已实现

- 新增 `user_llm_settings` 表，每个用户一条记录，保存个人档案和当前选择。接口从认证身份取得 `user_id`，请求体不能指定配置所有者。删除用户时配置级联删除。
- API Key 通过 Fernet 加密后存入数据库，派生密钥绑定用户。接口只返回个人密钥掩码，基础模型密钥连掩码也不返回。个人档案不能修改只读基础档案。
- 基础模型默认 `glm-5.3-flash`。新用户只看到基础模型；可以新增自己的 OpenAI 兼容模型并保存、切换。清空个人档案会回到基础模型。旧全局档案没有自动分配给所有用户。
- 每次聊天冻结该用户的模型配置，通过请求上下文传递给实际 Agent、摘要调用和标题生成。只在所选个人模型及基础模型之间降级，不改变全局注册表，也不借用其他用户的 Key。已经开始的请求不会受之后切换模型影响。
- `/chatbot/chat` 和 `/chatbot/chat/stream` 的输入只接受 `role: user`；伪造 `system` 或 `assistant` 返回 422。系统指令与历史由服务端构建。
- 清空聊天在同一数据库事务中删除检查点并将 `session.context_state` 置空，提交成功后清除摘要段、Epoch、水位状态和会话记忆快照的进程缓存。失败时保留缓存，避免数据库与内存状态分裂。此处不删除用户长期记忆。
- Web 请求绑定发送时的会话及取消信号。切换会话/退出页面会取消旧流，延迟到达的旧片段不能更新新会话。历史请求不能覆盖生成中的本地回复。Mobile 保留会话绑定的本地 overlay，并校验片段所属会话、在卸载时取消请求。

## 摘要重复计算的原因（修复前）

根因是“累计摘要”和“独立分段”两种语义混用：

1. `manager.py` 读取水位时把所有段的 `covered_turn_count` 相加，再用这个数跳过原始轮次。
2. 再次压缩时，它把 `segments[-1]` 作为 `previous_summary` 传给 `SummaryManager.compact`。
3. `summary.py` 将上一段摘要内容加入提示词，并计算 `上一段覆盖轮数 + 本批轮数`，得到累计覆盖数。
4. `manager.py` 保留上一段，再追加这份包含上一段的摘要。下一次读取时，上一段被重复计算。

例如：

| 操作 | 保存的段计数 | 实际已压缩轮数 | 读取时求和 |
| --- | --- | --- | --- |
| 首批压缩 3 轮 | `[3]` | 3 | 3 |
| 再压缩 2 轮 | `[3, 5]` | 5 | 8 |

若至少有 8 轮历史，后续会错误跳过尚未进入摘要的第 6～8 轮。历史不足时，`min(..., len(all_turns)-1)` 将错误水位限制到历史上界，保护当前轮，但不能恢复被跳过的历史。

影响不仅是计数：摘要内容也重叠，重复占用上下文；段合并继续求和会保留错误；错误段写入 `session.context_state` 后，重启仍会恢复错误水位。

## 选定方案

推荐沿用现有独立分段设计：每个新段只概括本批新增轮次，覆盖数只记录本批轮数；旧段保持冻结，达到阈值时再合并互不重叠的段。段版本/标识需单独保持递增，不能简单把 `previous_summary` 置空后让所有段都成为 v1。

另一种方案是只保留一份累计摘要，每次替换旧摘要，用该摘要的累计覆盖数作为水位。它会持续重写旧信息，更容易发生多轮压缩后的信息损失，也不符合目前冻结旧段的设计。

无论采用哪一种，已有重叠摘要都需要修复。建议从仍保留的原始检查点重建摘要；只改新段计数不能修复数据库中已有的错误。若原始历史已被删除，不能声称可完整恢复遗漏内容。

现已实施独立分段方案和 V2 载荷；测试覆盖连续压缩、相邻合并、重启恢复、失效来源、失败回退、清空竞争和多 worker CAS。预算装不下的未摘要原文仅从本次请求窗口移出，原始 checkpoint 仍保留，水位线不会将它们误算为已摘要。
