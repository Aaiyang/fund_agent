## 2026-10-03～04｜Agent"失明"连环案：上下文修剪删空窗口 + resume 吞掉新消息 + 递归上限 500

### 问题现象

让 Agent「搜索当前基金（022287）的相关新闻」时，对话失败。这个问题跨了两天、表现递进，总共出现三层数据：

1. **第一层（10-03）**：模型连续 12 轮反复调用 `get_fund_holdings`，触发递归上限 25，抛出 `GraphRecursionError`，接口 500，前端收到英文原始报错。
2. **第二层（10-03 晚修复后）**：500 消失了，用户看到"处理步骤过多已中止"的友好提示——但模型**依然**在循环调工具，问题没被回答。
3. **第三层（10-04）**：在同一会话里换任何问法都失败。模型永远在盲目调工具，仿佛完全不知道用户在问什么。

后端日志里的决定性证据（第一天就存在，但被忽略）：发往 LLM 的请求里 `messages` 数组**只有一条系统提示词**——用户的问题、全部历史、工具结果统统不在。

### 问题出现的原因（四层缺陷连锁；⚠️ 第一版诊断曾归因于"模型行为缺陷"，是错的）

要理解这个 BUG，先要知道上下文是怎么装车的。每次请求，`prepare_messages`（`app/agent/context/manager.py`）把会话的全部历史消息做修剪：

- `strategy="last"`：从**最新一条**往前累加，装满 4096 token 预算为止；
- `start_on="human"`：装完后检查窗口**开头**，如果不是用户（human）消息，就把开头连续的非 human 消息删掉，直到开头是 human（很多模型 API 不允许上下文以 AI/工具消息开头）。

**第一层：会话被工具结果"喂胖"。** 用户分析 022287 时，Agent 每轮调 `get_fund_holdings`，返回前十大重仓 + 行业配置 + 10 只股票实时行情——单条工具消息上千 token。会话线程最终膨胀到 **213 条消息**，其中**最后 195 条全是 AI/tool 消息，没有一条 human**（最后一条 human 停在第 17 位，是很早之前的提问）。

**第二层：修剪器把用户的问题"删没了"（核心 BUG）。** 线程超过 4096 预算的那一刻：

```
线程：[human(很早的问题), ai, tool, ai, tool, ... ai, tool]   ← 共 213 条
                                    ↑
        从尾部装 4096 token：窗口落在纯 tool/ai 区域（约最后 4~6 条）
                                    ↑
        start_on="human"：窗口开头不是 human？删！
        删完还不是？再删！……把窗口里所有消息删光
                                    ↑
        修剪结果：空 → 发给 LLM 的 messages = [系统提示词] 仅此一条
```

`strategy="last"`（取最新）和 `start_on="human"`（必须以 human 开头）两个设计单独看都对，**在长工具链场景下互相打架**：预算窗口落在没有 human 的尾巴里，start_on 就把窗口整段删空。结果模型收到的是一个"只有工具列表、没有问题"的空提示词——**模型是瞎的**，它不知道用户问了什么，只能盲目调工具，试完一个再看下一个。

**第三层：循环打满上限，崩出一个"毒状态"。** 12 轮循环后撞上 `recursion_limit=25`（保险本身没问题），LangGraph 抛 `GraphRecursionError`，但代码没有捕获 → 接口 500。更糟的是崩溃时 checkpoint 里留下了挂起任务：`state.next = ('tool_call',)`。

**第四层：resume 机制把会话"锁死"（解释了为什么换问法也没用）。** `get_response` 有一条规则：`state.next` 非空就走恢复（resume）路径——这是为人工确认（ask_human 中断后等用户答复）设计的，但它不区分"等人工确认"和"崩溃遗留的半死任务"。于是用户之后发的每一条消息都被当成 **resume 值**塞进死掉的循环里，而 resume 机制**不会把新消息写进对话线程**——这个会话永久卡死，换什么问法都一样。

另外要澄清：联网搜索工具和持仓工具单独测试**都是好的**（能搜到 022287 的新闻、能返回持仓数据）。工具层没有故障，故障在更上层的上下文组装与恢复逻辑。

### 解决办法

1. **修剪兜底：用户最新提问永远保留**（`app/agent/context/manager.py` 的 `prepare_messages`）。修剪后如果窗口为空、或开头不是 human，回退为"从最后一条 human 开始的切片"，再由新增的 `_fit_budget` 在预算内保留尽量新的消息——**用户的提问永远保留**，老的中间消息优先丢弃。这样模型永远能看到用户在问什么。
2. **resume 甄别：区分人工确认与崩溃遗留**（`app/agent/graph/agent.py`）。新增 `_pending_interrupt(state)`：只有挂起任务带有 `interrupts`（真的人工确认）才走 resume 恢复；崩溃遗留的挂起节点按**全新提问**处理——用户的新消息通过 `add_messages` 正常进入对话线程，旧的死循环被新运行自然覆盖。
3. **递归上限友好降级**（同文件，第一天修复，保留）：`get_response` / `get_stream_response` 捕获 `GraphRecursionError`，返回"这个问题需要的处理步骤过多，已中途停止"的中文提示，而不是 500。作为最后一道防线。
4. **提示词重试约束**（`system.md`，第一天修复，保留）：同一工具同样参数失败后不要原样重试；新闻类问题用联网搜索、数据类问题用业务工具。

### 验证结果

- 用真实的中毒会话（checkpoint 里 213 条消息）直接跑修复后的 `prepare_messages`：输出从 **1 条（只有 SYS）变为 17 条**——首条系统提示词，第二条就是用户的原话「可以帮我搜索一下关于当前基金的相关新闻吗」，其后是本轮工具结果。
- `_pending_interrupt` 对该会话正确判定"非 HITL 中断 → 按新提问处理"。
- 新增回归测试：用一个"无论收到什么都要求继续调工具"的假 LLM 模拟无限循环，断言最终返回友好提示而非异常。
- 全量 261 个测试通过，ruff / pyright 零告警。

### 经验教训

- **"模型胡乱调用工具"先查它到底看到了什么**。openai 客户端的 debug 日志里就有发往 LLM 的完整 messages，第一天看一眼就能发现模型是"瞎"的。归因顺序应该是：模型看到了什么 → 为什么会看到这些 → 最后才是"模型蠢"。
- **`start_on="human"` 这类修剪参数有删空窗口的副作用**。"取最新 + 必须以 X 开头"在长工具链场景下会互相打架。凡是用 start_on 类修剪参数的地方，都要加"窗口删空时兜底保留最后一条用户消息"的保险。
- **崩溃后的挂起状态（state.next）要甄别后再恢复**。挂起 ≠ 应该恢复：只有带 `interrupts` 的人工确认才走 resume；否则用户后续消息会被 resume 机制静默吞掉，会话表现为"永久失灵"。
- **工具结果是大体积上下文的主要来源**。单条持仓工具消息上千 token，几轮就能撑爆修剪预算。新增返回大结果的工具时，必须在工具内部做裁剪或摘要。
- **文档里的诊断要允许被推翻**。第一版把根因写成"模型行为缺陷"并整理进了本文档，第二天被真实 checkpoint 的证据证伪——学习笔记要跟着修正，错误结论比没有结论更危险。

## 2026-10-07｜上下文预算与摘要的四连问题：摘要复述 / 口径漂移 / 尾部漏账 / 静默实施失败

### 问题现象

KV Cache 优化（去时间戳、Dynamic Tail、分段摘要）上线前后，连续撞到四个相互纠缠的问题：

1. **摘要被模型原样复述**：会话挂上"此前对话摘要"段后，模型把摘要当成待办清单，逐条向用户复述（"根据之前的对话，你问了……"）。
2. **预算口径漂移**：预算管理器用"每轮估好再整体判断"的口径选择保留哪些 Turn，最终校验却用"逐条计数"的口径——同一份上下文两把尺子量出 20-30 token 的差。预算贴边时这点口径差足以让最终结果越线（CONTEXT_BUDGET_EXCEEDED）或悄悄超限。
3. **固定成本漏账**：系统提示词与 Dynamic Tail（AgentStatus 等每轮变化的尾部）不随 Turn 增减，但预算选择时只数了 Turn——每一项"合法"，总和却超支，最后只能挤掉用户消息。
4. **静默实施失败**：把"绝对时间从系统提示词移除"的修复用 `str.replace` 打补丁，脚本没断言替换真的发生——时间仍在渲染、预算依旧报错，而"回归测试"恰好通过（同一秒内两次调用，时间戳字符串相等，断言形同虚设）。几天后才发现修复从未生效。

### 原因

1. 提示词没告诉模型摘要的**消费方式**——对模型来说一段"# 此前对话摘要"和一段用户消息没有本质区别，没有规则它就按"任务简报"处理。
2. 两条计数路径各自演化：选择器用 `Turn.estimated_tokens`（估算），校验用 `TokenEstimator.count_messages`（逐条）。启发式与真实口径的差值在"刚好贴边"的场景必然翻车。
3. 固定成本（system/tail/status）与可变成本（Turn）在预算会计里没有分科目。
4. 三重叠加：批量替换无断言 → 回归测试无差异制造（同秒比较恒真）→ 出现反证证据（发往 LLM 的 messages 里只有 system）时没有当场追问。

### 解决办法

1. **摘要消费规则写进提示词**：组装时给摘要段加"仅供你参考的背景信息，不要在回答中原样复述"前缀；`conversation_summary.md` 的输出约束禁止待办清单式表述。
2. **计数统一到单一实现**：`count_messages = Σ count_message`（逐条 4+内容），Turn 估算也走同一函数——任何分组方式求和恒等，两把尺子并成一把。
3. **固定成本入账**：预算选择先扣 system/tail/status 固定开销，Turn 只在剩余额度里竞争。
4. **机制性逐出兜底**：组装完成后用真实计数逐出最老的未压缩 Turn，直到总量精确合规——口径差再多也兜得住。
5. **实施必须带断言**：替换脚本 `assert old in new`；回归测试人为制造差异（monkeypatch 时钟跨秒）；出现与预期不符的日志当场停下追问，不带病前行。

### 验证结果

- 全量测试通过（含口径统一、逐出循环、分段合并、持久化恢复的新回归）；ruff / pyright 零告警。
- 两把尺子合一后，`count_messages` 对任意分组求和恒等，选择口径与校验口径的差值归零。
- 时间戳移除的修复用"monkeypatch 时钟制造跨秒差异"的测试重新锁定。

### 经验教训

- **静默失败比崩溃更危险**。崩溃有堆栈，静默失败只有"看起来修好了"。批量替换必须断言命中次数；验证必须包含"修复前后应有可观测差异"这一条。
- **同一份东西只能有一把尺子**。凡是估算值与精确值并存的地方，贴边场景必然翻车——要么统一口径，要么在最后用精确值兜底。
- **给模型的每一段内容都要写明消费方式**。背景材料不写消费规则，模型就会拿它当任务简报复述。
- **预算会计要分科目**。固定成本、可变成本、余量分开记账，否则"每一项都合法，总和却超支"。
